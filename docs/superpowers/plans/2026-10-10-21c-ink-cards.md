# ink cards and lorebooks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `ink cards` and `ink lorebooks` list, search, show, create, edit in `$EDITOR`, list history, archive, export, and import a file.

**Architecture:** One builder makes the commands both types share, from a `kind` that names the type in URLs and messages. Every command calls an existing API route: `POST /search` and `POST /lorebooks/search`, `GET`, `POST` and `PUT` on `/<plural>[/{id}]`, `GET /<plural>/{id}/revisions`, `PUT /<plural>/{id}/archived`, `POST /bulk`, `POST /blobs`, and `POST /imports`. The server doesn't change.

**Tech Stack:** Go 1.27, `github.com/spf13/cobra`.

Ticket: INN-21, slice 21c. The slices are listed in `docs/superpowers/plans/2026-10-07-21a-ink-client.md`.

Decisions recorded during planning:

- `list` is `search` with no text. Both print one page, 50 rows by default; `--limit` and `--page` pick another. When more rows match, a line on stderr names the next page. `list --archived` lists archived ones.
- `search` takes text, or a whole query as JSON when the argument starts with `{`, as `archive` does.
- `create` and `edit` take the CCv3 `data` object, or a whole card or lorebook file (`{"spec": ..., "data": {...}}`), whose `data` they send.
- `edit <id>` opens the head revision's data in `$VISUAL`, then `$EDITOR`, then `vi` (`notepad` on Windows), and saves only if it changed. When the save fails, the edited file stays and the error names it, so the edit isn't lost. `edit <id> <file>` skips the editor, for scripts.
- `archive` and `unarchive` take an ID as well as a query. An ID archives that one entity directly; a query starts a bulk job, as today.
- `import <instance-id> <file>` uploads the file as a blob and imports it with the importer instance, as the README's curl recipe does. The instance decides whether the file is a card or a lorebook, so both namespaces run the same command.
- `ink lorebooks export` writes `{"spec": "lorebook_v3", "data": ...}` from `GET /lorebooks/{id}`. The API has no lorebook export, and the CCv3 standalone lorebook format is only that wrapper, so the client builds it. Lorebooks have no codec formats.
- `ink lorebooks sources` reuses the cards command, since the routes match.
- Row types stay local structs in `cmd/ink`, as in 21a. Nothing new goes in `internal/wire`.
- `stubAPI` answers a POST with its reply for the path when it has one, so tests can stub search results.

Not in this slice: restoring or comparing revisions, tags, and lorebook links. `ink call` reaches them.
