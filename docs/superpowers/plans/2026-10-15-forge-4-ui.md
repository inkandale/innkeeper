# Forge Phase 4: The Forge's AI Interface Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The card page and the new-card page run plugin actions: tabs, the Reforge panel with mentions, field menus, the running header, Review, Report, Refine, and images.

**Architecture:** INN-57, phase 4 of `docs/superpowers/specs/2026-10-14-forge-design.md`, "The Forge page". Phase 2 serves everything the UI needs: `GET /actions`, `POST /actions/runs`, `GET /jobs?kind=action&card_id=`, and an action job whose progress is `{message, done, total, result?}`. The UI keeps no run state of its own beyond the jobs: a run is its job, its starting data is the job's `payload.entity.data`, and its result comes from getting the single job, since lists and streams cut `result`.

Pieces, all in a new `web/src/forge/` folder except where noted:
- **`actions.ts`**: types for actions, runs, results, and reports; scope and locks; which action the instruction box and the Start tab run; changed keys; the Refine instruction; the settled-runs store.
- **`mentions.ts`**: the mention types list, parsing `@type/name` out of text, and resolving picked and typed names.
- **`useForge.ts`**: the actions list, the model setup choice, the card's runs from the job list, starting, waiting, stopping, and settling runs.
- **Components**: `Forge.tsx` (tabs, ⌘K, field menus and badges, Start), `Reforge.tsx` (the panel), `Inputs.tsx` (an action's inputs and images, and the model setup picker), `MentionBox.tsx`, `RunHeader.tsx`, `Review.tsx`, `Report.tsx`, `Hammer.tsx`, `Forge.css`. The logic file isn't `forge.ts` because macOS file names ignore case and `Forge.tsx` exists.
- **Go**: a `name` search filter, so autocomplete and typed mentions can find cards and lorebooks by part of their name; full-text search has no prefix match. And `jobs.Run.SaveProgress`, which an action run calls on each progress message: the worker otherwise saves progress only at lease renewal, every 10 seconds, too late for the running header.

**Tech Stack:** React, TypeScript, TanStack Query, Vitest and Testing Library; `react-markdown` (new, sanctioned by the spec); Go and PostgreSQL for the filter.

**Tests:** Go DB tests run with `INNKEEPER_TEST_DATABASE_URL=postgres://postgres:postgres@localhost:55432/postgres`. Web tests run with `npm test` in `web/`.

**Decisions:**
- **Unreviewed runs.** A run is *settled* once the owner applies or discards its proposal, or dismisses its finished line. Settled job IDs live in `localStorage` under `innkeeper.forge.settled`, newest 500, read and written in `try`/`catch`. Without storage, finished runs from the last 20 come back after a reload, which is safe. After a reload the Forge shows the card's unfinished runs and its unsettled finished ones from `GET /jobs?kind=action&card_id=…&limit=20`, fetching each unsettled one for its result.
- **The report** on the Report tab is the newest finished run with a report, whether settled or not, so a report and its badges survive a reload.
- **Review** shows one proposal at a time, the oldest unsettled one with changes. Review opens on its own when a proposal arrives.
- **Waiting.** A run whose scope overlaps a live run's waits in the browser and starts, from the draft as it is then, once the overlap clears. A report-only run never waits. A waiting run is lost on reload, since it never started.
- **The instruction box** runs the whole-card `card` action with `instruction: true`. The Start tab runs the `new` action, its concept box filling that action's instruction. The point of view is the `new` action's `inputs`, rendered with `SchemaForm`, so no plugin's input names are known to core.
- **On a new card**, the hammer button and ⌘K open the Start tab. Runs on a new card aren't picked up after a reload: the job list finds runs by `card_id`, and a new card has none.
- **Mention names.** A typed mention resolves to the longest library name the text continues with, so `@lorebooks/Northern Reach` works typed by hand. The server lookup is by the first word, with the new `name` filter.
- **Images.** For an action with `images: true`, the owner can drop a reference image and tick "Send the avatar too". A new file is uploaded with `upload()` when the run starts; a card's avatar is already a blob, so only its SHA is sent.

```ts
export type Named = { id: number; name: string };
/** A mention type: what follows @ and how its names are found. Adding one is one entry here. */
export type MentionType = { key: "cards" | "lorebooks"; noun: string; find: (name: string, size: number) => Promise<Named[]> };
export const mentionTypes: MentionType[] = [
  { key: "cards", noun: "card", find: (q, n) => findNamed("card", q, n) },
  { key: "lorebooks", noun: "lorebook", find: (q, n) => findNamed("lorebook", q, n) },
];
export type Picked = Named & { type: string };
export type Mention = { start: number; end: number; type: string; word: string; name: string; state: "ok" | "unknown" | "ambiguous" | "pending"; id?: number };
export function mentionsIn(text: string, picked: Picked[], lookup: (type: string, word: string) => Named[] | undefined): Mention[];
export function suggestAt(text: string, caret: number): { at: number; type?: MentionType; query: string } | null;
export function contextOf(mentions: Mention[]): { cards?: number[]; lorebooks?: number[] };
```

`findNamed` posts `{filter: {name}, fields: ["name"], sort: "name", page: {size}}` to the kind's search route. A picked entry wins over a typed lookup when its name follows `@type/` at a word boundary; the longest wins.
