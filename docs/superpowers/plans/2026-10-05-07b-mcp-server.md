# MCP Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve MCP at `/mcp` on `innkeeper-api`, with the spec's tools, for callers with an API token.

**Architecture:** `internal/mcp` builds one MCP server per tier, each listing only the tools that tier allows. The SDK's Streamable HTTP handler runs stateless and picks the server from the caller's token. Each tool turns its arguments into an API request, serves it with the API's own handler in process with the caller's `Authorization` header, and returns the response as JSON text, or a tool error with the status and message.

**Tech Stack:** Go 1.27, `github.com/modelcontextprotocol/go-sdk` v1.8.0 (new), its `auth` package for bearer checks.

**Spec:** `docs/superpowers/specs/2026-10-05-mcp-server-design.md`, "Tools" and "Architecture". Build order step 2.

**Kaneo:** INN-7.

## Design notes

- **Stateless.** No sessions to share between API processes. The cost: a change to plugin tools (plan 7c) shows up on the client's next `tools/list`, not through `notifications/tools/list_changed`.
- **Auth.** `auth.RequireBearerToken` wraps the handler with a verifier that calls `Auth.CheckToken` and returns the tier as the token's only scope. API tokens don't expire, so `AllowMissingExpiration` is set. Cookies aren't read.
- **Dispatch.** `api.Server.Handler()` is built once; the MCP package gets it as an `http.Handler`. A tool builds `httptest.NewRequest`, copies `Authorization` from `CallToolRequest.Extra.Header`, serves it into a `httptest.ResponseRecorder`, and maps the result. The API checks the tier again, so a tool listed by mistake still can't act above the caller.
- **Writes** send `"source": "mcp"`.
- **Tool table.** Each tool: name, description, tier, input type (the SDK derives the schema), and a function from input to request. Tools that need two calls (`get_card` with bindings) make both.
- **Errors.** A non-2xx response is a tool error whose text is `<status>: <detail>` plus any error details, such as the new preview on a `409` from `push`.

## Tools

As the spec's table. Inputs:

| Tool | Input |
|---|---|
| `search_cards` | `query`: the `POST /search` body |
| `get_card`, `get_lorebook` | `id` |
| `get_history` | `kind` (`card` or `lorebook`), `id` |
| `create_card`, `create_lorebook` | `data`, optional `message` |
| `update_card`, `update_lorebook` | `id`, `base_revision_id`, `data`, optional `overrides`, `message` |
| `link_lorebook`, `unlink_lorebook` | `card_id`, `lorebook_id` |
| `restore_revision` | `kind`, `id`, `revision_id` |
| `preview_push` | `kind`, `id`, `instance_id` |
| `push` | `kind`, `id`, `instance_id`, `confirm`, optional `new_copy` |
| `check_drift` | `binding_id` |
| `adopt` | `binding_id`, `into`, optional `base_revision_id` |
| `list_bindings` | `kind`, `id` |
| `list_jobs` | none; `get_job`, `cancel_job`: `id` |
| `start_import` | `instance_id`, optional `path` |
| `list_plugins`, `list_instances` | none |
| `create_instance` | `plugin`, `name`, optional `config`, `secrets`, `owner_subject` |
| `update_instance` | `id`, optional `name`, `config`, `secrets`, `owner_subject` |

`push` requires `confirm`, unlike the API, so an MCP client always pushes what it previewed. `create_instance` and `update_instance` are `destructive`, as their routes are.

## Plan series

- **Plan 7c (plugin tools):** stateless servers are built per tier at startup; plugin tools need a server built per request, or a short cache keyed by the instances' update times.
- **Plan 7d (OAuth):** the verifier also accepts OAuth access tokens. Dispatch must let those through to the API only for requests it makes, since they are valid only on `/mcp`.
